# C06 — Internal Evidence Assessment

## Ověřte cizí projekt proti tomu, co měl tým skutečně splnit v C01–C05

### Co je cílem?

Dnes nenavrhujete další funkcionalitu ani nový dokument.

Dostanete projekt jiného týmu a ověříte:

Odpovídá to, co tým specifikoval a navrhl, tomu, co skutečně implementoval a ověřil?

Nehodnotíte, zda byste projekt navrhli jinak.

Hodnotíte konzistenci a evidence vůči zadáním C01–C05.

# Co budete na konci mít?

Odevzdáte:

1. jeden vyplněný assessment checklist;

2. konkrétní evidence u každé odpovědi;

3. maximálně **3 významné candidate findings**;

4. technické ověření těch findings, které považujete za skutečné;

5. reakci vlastníků projektu: přijmout / odmítnout / odložit / není třeba měnit.

# Jak odpovídat v checklistu

Používejte jen:

| Odpověď | Význam |
|---|---|
| **YES** | Splněno a našli jste konkrétní evidence. |
| **PARTLY** | Něco existuje, ale není to úplné, jednoznačné nebo dostatečně podložené. |
| **NO** | Požadovaný stav neexistuje, chybí evidence nebo je zjištěna nekonzistence. |
| **N/A** | Bod opravdu není relevantní. Musíte stručně napsat proč. |

Ke každé odpovědi zapište Evidence.

Dobře:

YES Evidence: docs/specification.md — R-07 src/AvailabilityService.cs — isAvailable() tests/AvailabilityTests.cs — confirmedOverlapIsRejected()

Špatně:

YES — vypadá to dobře.

# Důležité pravidlo

## Nekontrolujete nic, co předchozí zadání nepožadovala.

Není finding, že tým:

• nepoužil váš oblíbený framework;

• nepoužil určitý design pattern;

• nemá konkrétní procento coverage;

• nemá SonarQube;

• nemá CI pipeline;

• nemá další diagram, který nebyl požadován;

• udělal jinou, ale konzistentní engineering decision.

C06 nesmí zpětně přidávat požadavky do C01–C05.

# Organizace

Budete hodnotit projekt jiného týmu.

Team A → Team B Team B → Team C Team C → Team D ... last team → Team A

Pracujte vždy nad jednou konkrétní baseline.

Repozitář může být GitHub, GitLab, Bitbucket, školní Git nebo jiný systém.

# 0 — Převzetí projektu

Od hodnoceného týmu si vezměte:

Project name: Assessed commit / tag: ZIP stejné verze: How to build: How to run: How to run tests: Path to C02 artifacts: Path to C03 artifacts: Path to C04 evidence: Path to C05 artifacts:

Pokud používáte přímo repository, stále si zapište konkrétní commit/tag.

# 1 — BASELINE / C01

C01 vytvořilo společný projekt, scope a základ, ze kterého později vznikl runnable product.

Nehodnotíte znovu historický engineering spike.

Ověřujete pouze, zda je současná hodnocená verze jednoznačná a použitelná pro assessment.

| ID | Co přesně udělejte | Odpověď | Evidence |
|---|---|---|---|
| B1 | Najděte commit/tag a ověřte, že dokumentace, code a tests patří ke stejné baseline. |  |  |
| B2 | Podle instrukcí spusťte relevantní část aplikace **nebo alespoň její testy**. |  |  |

### Pokud projekt nejde rychle spustit

Nestravte celé cvičení opravou cizího prostředí.

Zapište například:

B2 = NO Evidence: README requires database X but configuration/example is missing. Tests cannot be executed from the submitted baseline.

Pak pokračujte statickým assessmentem.

# 2 — C02 ENGINEERING SPECIFICATION

V C02 měl tým specifikovat mimo jiné:

• Create Reservation;

• Check Availability;

• Confirm Reservation;

• Cancel Reservation;

• business rule / invariant;

• preconditions / postconditions;

• state model;

• verification;

• konzistenci specifikace, stavů a implementace.

## Co máte vybrat

Vyberte:

1. **jednu ze čtyř operací**;

2. **jeden významný business rule / invariant**.

Nepokoušejte se projít celý systém.

## Checklist C02

| ID | Co přesně udělejte | Odpověď | Evidence |
|---|---|---|---|
| R1 | Najděte vybranou operaci. Zkontrolujte její vstup, precondition, výsledek/postcondition a případnou změnu state. |  |  |
| R2 | Najděte jeden business rule/invariant a napište vlastními slovy, co přesně zakazuje nebo garantuje. |  |  |
| R3 | Porovnejte operaci + business rule se state modelem. Neodporují si? |  |  |
| R4 | Najděte konkrétní code path, který operaci/rule realizuje. Odpovídá implementace specifikované semantics? |  |  |
| R5 | Najděte test nebo jinou verification evidence pro vybranou operaci/rule. Ověřuje skutečně daný claim? |  |  |

### Příklad

Claim: Two CONFIRMED reservations of the same exclusive resource shall not overlap. R4 = NO Expected: CONFIRMED overlap is rejected. Observed: isAvailable() filters only DRAFT reservations. Evidence: docs/specification.md R-07 src/AvailabilityService.isAvailable()

# 3 — C03 ARCHITECTURE

V C03 měl tým vytvořit zejména:

• architecture drivers;

• functional responsibilities;

• ownership;

• alternatives + trade-off;

• ADR;

• structural view;

• significant dynamic scenario;

• relevant state/data ownership;

• implementation a architecture conformance.

## Co máte vybrat

Vyberte:

1. **jednu významnou architecture responsibility**;

2. **jednu významnou interaction** z dynamic view;

3. **jedno ADR / významné architecture decision**.

## Checklist C03

| ID | Co přesně udělejte | Odpověď | Evidence |
|---|---|---|---|
| A1 | Najděte vybranou responsibility a jejího ownera v architecture artifacts. Je ownership jednoznačný? |  |  |
| A2 | Najděte v code skutečného ownera této responsibility. Odpovídá architecture view? |  |  |
| A3 | Vezměte jednu interaction ze sequence/dynamic view a projděte skutečný call path v code. Odpovídá? |  |  |
| A4 | Najděte jedno ADR/decision. Je rozhodnutí stále viditelné v současné implementaci, nebo bylo změněno bez aktualizace evidence? |  |  |

### Nehledejte „lepší architekturu“

Správná otázka není:

„Já bych to udělal přes Strategy.“

Správná otázka je:

„Tým tvrdí X. Realizuje současný systém skutečně X?“

# 4 — C04 QUALITY & MEASUREMENT

V C04 měl tým vzít konkrétní quality concern a projít:

Quality Concern → Evaluable Criterion → Measurement / Evidence → Trade-off / Decision

## Co máte vybrat

Použijte přesně quality concern, které si tým zvolil v C04.

Nevymýšlejte mu jiné.

## Checklist C04

| ID | Co přesně udělejte | Odpověď | Evidence |
|---|---|---|---|
| Q1 | Najděte quality concern a evaluable criterion. Lze podle criterion jednoznačně rozhodnout, zda výsledek vyhovuje? |  |  |
| Q2 | Najděte measurement/evidence. Měří skutečně definovaný criterion za deklarovaných podmínek? |  |  |
| Q3 | Najděte engineering decision. Odpovídá tomu, co measurement skutečně ukázal? |  |  |

### Příklad

Criterion: p95 < 250 ms for 50 concurrent requests Evidence: one manually measured request = 83 ms Q2 = PARTLY Reason: the evidence measures neither p95 nor the declared workload.

# 5 — C05 DETAILED DESIGN & UNIT VERIFICATION

V C05 měl tým rozpracovat jednu architecture responsibility / software unit a ukázat:

• detailed responsibilities;

• ownership;

• významné interfaces/contracts;

• focused structural view;

• detailed behavior/sequence;

• significant methods/operations;

• algorithm/decision logic, pokud je relevantní;

• unit/component tests odvozené z DD;

• DD ↔ implementation consistency.

## Co máte vybrat

Použijte software unit, kterou tým skutečně rozpracoval v C05.

## Checklist C05

| ID | Co přesně udělejte | Odpověď | Evidence |
|---|---|---|---|
| D1 | Najděte design intent jednotky: responsibilities + významné methods/contracts/algorithm/state. Je z něj pochopitelné, jak má jednotka fungovat? |  |  |
| D2 | Porovnejte DD se skutečným code. Odpovídají významné methods, contract, state nebo algorithm? |  |  |
| D3 | Najděte unit/component tests uvedené jako evidence C05. Lze ukázat, z které části DD byly odvozeny? |  |  |
| D4 | Projděte významné branches / boundaries / states / failures popsané v DD. Jsou relevantní varianty ověřeny? |  |  |
| D5 | Vyberte jeden test a zkontrolujte jeho expected result / oracle. Vychází z design/specification, nebo pouze kopíruje současné chování code? |  |  |

### Příklad — interval overlap

DD:

conflict iff: existing.state == CONFIRMED AND existing.start < requested.end AND requested.start < existing.end

Relevantní případy mohou být:

existing 10:00–11:00 09:00–10:00 → no conflict 09:30–10:30 → conflict 10:00–11:00 → conflict 10:30–11:30 → conflict 11:00–12:00 → no conflict CANCELLED overlap → according to specification

Nejde o to mít hodně testů.

Jde o to, zda testy ověřují významná rozhodnutí z DD.

# 6 — VOLITELNÉ VERIFICATION TECHNIQUES

Pro hledání candidate findings můžete použít:

• manual review;

• IDE/compiler warnings;

• static analyzer;

• dependency analysis;

• test runner;

• coverage tool;

• AI code review;

• vlastní dočasný verification test.

Ale:

Tool warning není automaticky finding. AI output není automaticky finding.

Obojí je pouze podnět k ověření.

# 7 — Vyberte maximálně 3 candidate findings

Projděte všechny položky s:

PARTLY NO

Vyberte nejvýznamnější, maximálně 3.

Preferujte:

1. rozpor specification ↔ code;

2. rozpor architecture/DD ↔ code;

3. chybějící nebo nesprávnou verification evidence;

4. quality decision nepodložené measurement.

Neřešte kosmetiku.

# 8 — Technicky každý finding ověřte

Candidate finding se stane VERIFIED až po konkrétním ověření.

Použijte alespoň jednu techniku:

inspect concrete code path run existing test add temporary verification test reproduce behavior compare state/sequence/algorithm with code repeat measurement static-analysis evidence + manual confirmation

Pokud candidate nepotvrdíte:

REJECTED CANDIDATE

To je správný engineering výsledek.

# 9 — Zapište finding

Použijte:

Finding ID: Source: C02 / C03 / C04 / C05 Engineering claim: Expected: (reference to team's own artifact) Observed: Evidence: Verification performed: Result: VERIFIED FINDING / REJECTED CANDIDATE

Maximálně 3.

# 10 — Owner review

Předložte findings vlastnímu týmu.

Vlastník u každého zapiše:

ACCEPTED — change required ACCEPTED — no immediate change Reason: ... REJECTED Evidence: ... DEFERRED Missing information: ...

NO CHANGE REQUIRED je validní rozhodnutí, pokud je podložené.
